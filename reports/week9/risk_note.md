**Who wrote it:** the Northgate claims platform team (`claims-system` v0.3.1, one 176-line stdlib Python file vendored at `mcp_servers/claims_system/server.py`). It is unsigned and its hash is not pinned, so it runs as us, with our Python, our filesystem and our network.
**What it reaches:** all 40 claims, open and closed, in `data/claims/`. `get_claim_status` also returns the claimant's name, which no triage question needs. As a local process it could read any file we can read, `.env` included. Our client passes it only `CLAIMS_API_TOKEN` and never `GROQ_API_KEY`, but nothing sandboxes its file access.
**What it logs:** one line per call to `logs/claims_system.log`: UTC time, tool, the claim number exactly as typed (not validated first, so a newline in the argument can forge a log line), the outcome and an 8-hex SHA-256 fingerprint of the token. No names, but the log records which claims were looked at and when. Its results flow into our model context and on to Groq.
**What a stolen token does:** the server accepts ANY non-empty `CLAIMS_API_TOKEN`. There is no per-caller or per-claim scope and no expiry, so whoever holds a token can bulk-read the claimant, status and every adjuster note on every open and closed claim. The fingerprint lets us spot that use afterwards; it cannot stop it.
**Ship or don't:** don't ship it direct-to-agent as `mcp_config.json` wires it today. Ship it only behind the gateway (`mcp_config.gateway.json`: scoped caller token, adjuster notes denied unless granted, one audit line per call), with the file's hash pinned, and once the platform team drops `claimant_name` from `get_claim_status` and escapes the log fields.
